# T-0016: Numbering creation — programmatic abstract numbering definitions and list styles

**Status**: BLOCKED | **Size**: L
**Phase**: —
**Blocked by**: T-0015 (schema review may reveal new numbering-related elements)

## Context
The gap analysis marks `w:abstractNum` creation as **high priority**. python-docx can read and apply existing numbering definitions, but cannot create new abstract numbering definitions or list styles from scratch. This is one of the most-requested features — users need to programmatically create numbered and bulleted lists without relying on pre-existing styles in the template document.

## Acceptance Criteria
- [ ] Can create a new `w:abstractNum` definition with level formatting (indent, number format, text pattern)
- [ ] Can create a new `w:num` instance referencing an abstract definition
- [ ] Can apply the new numbering to paragraphs
- [ ] Supports common patterns: decimal, bullet, letter (upper/lower), roman (upper/lower)
- [ ] Level overrides work with created definitions
- [ ] Round-trip fidelity: created numbering survives save/reload
- [ ] Word opens the resulting document correctly
- [ ] All existing numbering tests continue to pass

### Anti-Pattern Warnings

**For this task specifically:**

1. **Do not hand-craft XML strings in tests for expected output** — Use the project's `cxml` element builder or `unitdata` builder pattern (see `tests/oxml/unitdata/numbering.py`) for creating expected XML. Hand-crafted XML is fragile and hard to maintain.

2. **Do not forget schema ordering** — Per OOXML schema, `CT_Numbering` children must appear in order: `w:numPicBullet`, `w:abstractNum`, `w:num`, `w:numIdMacAtCleanup`. The `ZeroOrMore` declarations in `CT_Numbering` need correct `successors` to enforce this. Currently `CT_Numbering` only declares `num` with successors. Adding `abstractNum` requires placing it before `num` in the successor chain.

3. **Do not test only single-level lists** — The OOXML spec allows up to 9 levels (ilvl 0-8). Test at least a multi-level definition with 2-3 levels to catch issues with level indexing.

4. **Do not skip `w:nsid` generation** — Each `w:abstractNum` requires a unique `w:nsid` (namespace ID). This must be generated deterministically or randomly. Failure to include it may cause Word to corrupt the document. Use a hex string format matching existing patterns (e.g., `FFFFFF7C`).

5. **Do not skip `w:multiLevelType`** — Required child of `w:abstractNum`. Must be one of: `singleLevel`, `multiLevel`, `hybridMultilevel`. Most user-facing lists are `hybridMultilevel` or `multiLevel`.

6. **Do not forget font specification for bullets** — Bullet lists require `w:rPr/w:rFonts` with `w:ascii="Symbol"` (or Wingdings etc.) in the level definition. Without this, Word renders garbage characters instead of bullets.

7. **Do not test mocks instead of real XML** — The existing `tests/parts/test_numbering.py` heavily uses mocks. For new creation logic, include at least some tests that exercise real XML parsing (like `tests/oxml/test_document.py` does with `element()` from `unitutil.cxml`).

8. **Do not assume numbering part always exists** — `DocumentPart.numbering_part` auto-creates an empty one. Tests for the end-to-end flow must handle both cases: document with existing numbering part and document where one must be created.

9. **Do not skip the registration step** — New element classes (`CT_AbstractNum`, `CT_Lvl`) must be registered in `src/docx/oxml/__init__.py` via `register_element_cls()`. Forgetting this means `OxmlElement("w:abstractNum")` returns a generic `BaseOxmlElement` instead of the custom class, silently breaking all custom methods.

10. **Watch for `abstractNumId` vs `numId` confusion** — These are distinct ID spaces. `abstractNumId` identifies abstract definitions (0-based by convention), `numId` identifies concrete instances (1-based by convention). Mixing them up causes silent document corruption.

**Universal warnings:**

- Run tests, do not just write them
- Check the full test suite, not just new tests — regressions in `behave features/` are especially likely since numbered/bulleted list styles (`List Bullet`, `List Number`) already exist in the default template
- Do not skip the type checker — new classes with xmlchemy descriptors need careful typing
- Verify round-trip with actual save/load, not just XML serialization

## Approach

### Research Summary

**Codebase exploration:**

- `src/docx/oxml/numbering.py` -- Existing `CT_Num`, `CT_NumLvl`, `CT_NumPr`, `CT_Numbering` classes. `CT_Numbering` already has `add_num()` and `_next_numId`. **No `CT_AbstractNum` or `CT_Lvl` classes exist** -- these are the core new elements needed.
- `src/docx/oxml/__init__.py` -- Registration site. Currently registers `w:num`, `w:numPr`, `w:numbering`, `w:lvlOverride`, `w:abstractNumId`, `w:ilvl`, `w:numId`, `w:startOverride`. Does **not** register `w:abstractNum` or `w:lvl`.
- `src/docx/parts/numbering.py` -- `NumberingPart` with `new()` classmethod that hand-crafts XML strings for 2 abstract nums. `_NumberingDefinitions` proxy wraps `num_lst` only.
- `src/docx/oxml/xmlchemy.py` -- Declarative element class framework (`ZeroOrMore`, `ZeroOrOne`, `RequiredAttribute`, etc.). `ZeroOrMore` auto-generates `_lst`, `_add_`, `_insert_`, `_new_` methods.
- `src/docx/oxml/shared.py` -- `CT_DecimalNumber`, `CT_String`, `CT_OnOff` reusable element classes.
- `src/docx/oxml/footnotes.py` -- Best pattern reference for creating new element classes with `new()` class methods that build XML programmatically.
- `src/docx/oxml/comments.py` -- Another pattern reference: `CT_Comments.add_comment()` uses `parse_xml()` with f-strings for complex XML creation.
- `docs/dev/analysis/features/numbering.rst` -- Schema analysis showing `CT_Numbering` child ordering: `numPicBullet`, `abstractNum`, `num`, `numIdMacAtCleanup`.
- `src/docx/templates/default-docx-template/word/numbering.xml` -- Reference XML with 9 `abstractNum` definitions and 9 `num` instances. Shows required children: `nsid`, `multiLevelType`, `tmpl`, and per-level: `start`, `numFmt`, `lvlText`, `lvlJc`, `pPr/ind`, optionally `rPr/rFonts`.
- `tests/oxml/test_comments.py` -- Test pattern using `element()` from `unitutil.cxml` with cast.
- `tests/oxml/test_styles.py` -- Test pattern using `element()` + `xml()` for expected output comparison.
- `tests/parts/test_numbering.py` -- Existing tests use builder pattern from `tests/oxml/unitdata/numbering.py` and heavy mocking.
- `tests/roundtrip/document_generators.py` -- `DOCUMENT_GENERATORS` dict for registration; generators return `Document` objects.
- `tests/roundtrip/test_generated_documents.py` -- Parametrized round-trip framework.

**Key constraints:**

1. `CT_Numbering` currently only declares `num = ZeroOrMore("w:num", successors=("w:numIdMacAtCleanup",))`. Adding `abstractNum` requires declaring it with `successors=("w:num", "w:numIdMacAtCleanup")` to enforce schema ordering.
2. `w:abstractNum` and `w:lvl` must be registered in `oxml/__init__.py` via `register_element_cls()`.
3. Each `w:abstractNum` requires `w:nsid` (unique hex ID) and `w:multiLevelType` children per schema.
4. Bullet lists require `w:rPr/w:rFonts` with `w:ascii="Symbol"` in level definitions.
5. The `numbering_part` property on `DocumentPart` auto-creates a `NumberingPart` when absent, so tests must handle both cases.
6. `abstractNumId` (0-based) and `numId` (1-based) are distinct ID spaces -- mixing them corrupts documents.

**Relevant prior work:**

- No prior tasks have implemented CT_AbstractNum or CT_Lvl.
- `CT_Footnote.new()`, `CT_Comments.add_comment()`, and `CT_Num.new()` provide three different creation patterns to choose from.

**OOXML Schema (from ECMA-376, not in existing docs but inferable from template XML):**

```
CT_AbstractNum:
  children: nsid, multiLevelType, tmpl?, name?, styleLink?, numStyleLink?,
            lvl* (0..9), (plus extension children)
  attributes: abstractNumId (required, ST_DecimalNumber)

CT_Lvl:
  children: start?, numFmt, lvlRestart?, pStyle?, isLgl?, suff?,
            lvlText?, lvlPicBulletId?, legacy?, lvlJc?, pPr?, rPr?
  attributes: ilvl (required, ST_DecimalNumber), tplc?, tentative?
```

### Approaches Considered

#### 1. Minimal oxml classes + OxmlElement/parse_xml creation (P = 0.75)

**Description**: Define `CT_AbstractNum` and `CT_Lvl` as minimal `BaseOxmlElement` subclasses with only attribute and child element declarations (no `.new()` factory methods). Create instances using `OxmlElement()` and manual attribute/child setting, similar to how `CT_Num.new()` works. All creation logic lives in `CT_Numbering.add_abstractNum()` or helper functions.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | +/- | Matches `CT_Num.new()` partially, but CT_Num is simpler |
| Elegance | - | Complex XML structures (levels with sub-elements) get unwieldy with manual element creation |
| Surface area | + | Few files: `numbering.py` + `__init__.py` + tests |
| Risk | - | Manual element construction error-prone for deeply nested XML |
| Testability | + | Easy to test individual pieces |
| Reversibility | + | Contained in numbering module |

**Pros**: Minimal new code, stays close to existing `CT_Num` pattern.
**Cons**: The `CT_Lvl` element has many children (`start`, `numFmt`, `lvlText`, `lvlJc`, `pPr/ind`, `rPr/rFonts`); building this manually with `OxmlElement()` calls becomes verbose and error-prone. Does not give callers a clean object to configure levels after creation.

#### 2. Full declarative oxml classes with `.new()` factory methods (P = 0.85)

**Description**: Define `CT_AbstractNum` and `CT_Lvl` as full declarative classes using xmlchemy descriptors (`ZeroOrMore`, `ZeroOrOne`, `RequiredAttribute`) for child elements and attributes. Each class gets a `.new()` classmethod that creates a well-formed element. `CT_Numbering` is extended with an `abstractNum = ZeroOrMore(...)` declaration. A convenience method on `CT_Numbering` handles ID assignment and insertion. `NumberingPart` gets thin proxy methods that delegate to the oxml layer.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | + | Matches `CT_Footnote.new()`, `CT_Num.new()`, `CT_Comment` patterns |
| Elegance | + | Declarative child elements enable `get_or_add_*` patterns; clean factory methods |
| Surface area | +/- | `numbering.py` grows, `__init__.py` updated, tests in 3-4 files |
| Risk | + | Low -- follows proven xmlchemy patterns; complex but well-understood |
| Testability | + | Factory methods easily unit-tested; declarative descriptors well-tested by framework |
| Reversibility | + | All changes in numbering module family |

**Pros**: Most natural fit for the codebase. Declarative descriptors give you `abstractNum_lst`, `_add_abstractNum()`, `_insert_abstractNum()` for free. Factory methods (`CT_AbstractNum.new()`, `CT_Lvl.new()`) encapsulate XML construction. Level objects can be further configured after creation.
**Cons**: More code upfront, but follows the pattern that every other CT_* class uses.

#### 3. parse_xml with f-string templates (P = 0.72)

**Description**: Use the `parse_xml()` with f-string template approach (like `CT_Comments.add_comment()` and `NumberingPart.new()` already do) to create abstract numbering definitions. No new `CT_AbstractNum`/`CT_Lvl` classes -- just extend `CT_Numbering` with an `add_abstractNum()` method that builds the full XML string and parses it.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | +/- | Matches `CT_Comments.add_comment()` but that pattern is used for simpler structures |
| Elegance | - | Long f-strings for 9-level definitions are fragile; cannot access/modify levels after creation |
| Surface area | + | Minimal new code |
| Risk | - | String-based XML construction is fragile; no type safety on level configuration |
| Testability | - | Can only test final XML output, not individual components |
| Reversibility | + | Easy to replace |

**Pros**: Quick to implement, minimal new classes.
**Cons**: Anti-pattern for complex structures. The verification plan explicitly warns against this ("Do not hand-craft XML strings"). Multi-level lists with 9 levels produce enormous f-strings. No way to programmatically modify individual levels after creation. `NumberingPart.new()` already uses this pattern and it's already showing strain.

#### 4. High-level builder API with presets (P = 0.68)

**Description**: Create a `NumberingBuilder` or `ListDefinition` high-level class that provides a fluent API for defining lists (e.g., `ListDefinition.bullet()`, `ListDefinition.decimal()`). This sits above the oxml layer as a new proxy-level module (`src/docx/numbering.py` or similar). The builder generates the oxml elements internally.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | - | No precedent for builder pattern at proxy level; deviates from layer architecture |
| Elegance | + | Nice user-facing API |
| Surface area | - | New module, new classes, plus still needs oxml classes underneath |
| Risk | - | Over-engineering for this task; API design decisions that are hard to reverse |
| Testability | +/- | Builder tests needed in addition to oxml tests |
| Reversibility | - | Public API is harder to change later |

**Pros**: Best user experience with preset configurations.
**Cons**: Premature abstraction. The task scope is about oxml-layer creation + numbering part methods. A high-level API can be layered on later (and should be a separate task). This approach doubles the work without being required by the acceptance criteria.

#### 5. Extend existing CT_Numbering only (no new classes) (P = 0.55)

**Description**: Add `add_abstractNum()` directly to `CT_Numbering` that takes all configuration as parameters and constructs everything inline. No new `CT_AbstractNum` or `CT_Lvl` classes. Use `OxmlElement` for everything.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | - | Every other OOXML element type in this codebase has its own CT_* class |
| Elegance | - | Monolithic method with many parameters; no encapsulation |
| Surface area | + | 1 file modified |
| Risk | - | Unmaintainable; mixing concerns in CT_Numbering |
| Testability | - | Difficult to test level construction independently |
| Reversibility | +/- | Easy to delete, but hard to refactor into proper classes later |

**Pros**: Fewest new abstractions.
**Cons**: Violates the fundamental project pattern where each OOXML complex type gets its own class. Makes `CT_Numbering` a god class. Testing individual levels becomes impossible. The verification plan explicitly calls for `CT_AbstractNum` and `CT_Lvl` classes.

### Recommendation

**Selected**: Approach 2 -- Full declarative oxml classes with `.new()` factory methods

**Rationale**:
- Highest confidence (P = 0.85) due to strong alignment with every existing CT_* class pattern in the codebase
- Declarative xmlchemy descriptors (`ZeroOrMore`, `ZeroOrOne`) auto-generate the insertion/access methods needed, reducing manual code and bugs
- Factory methods (`CT_AbstractNum.new()`, `CT_Lvl.new()`) encapsulate the complex XML construction while keeping it testable at the unit level
- The verification plan explicitly names `CT_AbstractNum` and `CT_Lvl` as the classes to create/test
- Supports the red-green-refactor flow: tests can target individual factory methods before wiring into the numbering part

**Key implementation notes**:

1. **`CT_Lvl` class** in `src/docx/oxml/numbering.py`:
   - Declare children via xmlchemy: `start = ZeroOrOne("w:start", ...)`, `numFmt = ZeroOrOne("w:numFmt", ...)`, `lvlText = ZeroOrOne("w:lvlText", ...)`, `lvlJc = ZeroOrOne("w:lvlJc", ...)`, `pPr = ZeroOrOne("w:pPr", ...)`, `rPr = ZeroOrOne("w:rPr", ...)`
   - Attribute: `ilvl = RequiredAttribute("w:ilvl", ST_DecimalNumber)`
   - Factory: `CT_Lvl.new(ilvl, num_fmt, lvl_text, lvl_jc, start_val=1, indent_left=None, indent_hanging=None, font_name=None)` using `OxmlElement` calls (following `CT_Footnote.new()` pattern)
   - Successor ordering based on schema: `start, numFmt, lvlRestart, pStyle, isLgl, suff, lvlText, lvlPicBulletId, legacy, lvlJc, pPr, rPr`

2. **`CT_AbstractNum` class** in `src/docx/oxml/numbering.py`:
   - Declare children: `nsid = OneAndOnlyOne("w:nsid")`, `multiLevelType = OneAndOnlyOne("w:multiLevelType")`, `lvl = ZeroOrMore("w:lvl", successors=())`
   - Attribute: `abstractNumId = RequiredAttribute("w:abstractNumId", ST_DecimalNumber)`
   - Factory: `CT_AbstractNum.new(abstract_num_id, multi_level_type="hybridMultilevel")` creates element with `nsid` (random hex) and `multiLevelType`
   - Method: `add_lvl(ilvl, num_fmt, lvl_text, lvl_jc, ...)` to add configured levels

3. **Extend `CT_Numbering`**:
   - Add `abstractNum = ZeroOrMore("w:abstractNum", successors=("w:num", "w:numIdMacAtCleanup"))` **before** the existing `num` declaration (schema order matters for successor chains)
   - Add `_next_abstractNumId` property (like existing `_next_numId`)
   - Add `add_abstractNum()` method that creates and inserts with auto-assigned ID

4. **Registration** in `src/docx/oxml/__init__.py`:
   - Import `CT_AbstractNum` and `CT_Lvl` from `.numbering`
   - Register: `w:abstractNum` -> `CT_AbstractNum`, `w:lvl` -> `CT_Lvl`
   - Also register: `w:nsid` -> `CT_String`, `w:multiLevelType` -> `CT_String`, `w:numFmt` -> `CT_String`, `w:lvlText` -> `CT_String`, `w:lvlJc` -> `CT_String`, `w:start` -> `CT_DecimalNumber` (check which are already registered)

5. **`NumberingPart` extensions** in `src/docx/parts/numbering.py`:
   - `add_abstract_num(multi_level_type, levels)` -- delegates to CT_Numbering
   - `add_num(abstract_num_id)` -- already exists on CT_Numbering, expose via proxy
   - Extend `_NumberingDefinitions` to expose abstract numbering definitions

6. **Tests** (per verification plan):
   - `tests/oxml/test_numbering.py` -- New file: CT_AbstractNum, CT_Lvl, CT_Numbering extension tests
   - `tests/parts/test_numbering.py` -- Extend with proxy method tests
   - `tests/test_numbering_creation.py` -- New file: end-to-end creation scenarios
   - `tests/roundtrip/document_generators.py` -- Add `create_numbering_document()`
   - `features/` -- Add/extend behave scenarios

**Fallback**: If the full declarative approach encounters issues with xmlchemy descriptor ordering or complex child element relationships (e.g., `w:lvl` children that share tagnames with other contexts), fall back to Approach 1 (minimal classes + manual construction). The factory method signatures would remain the same, only the internal implementation would change from declarative to manual.
